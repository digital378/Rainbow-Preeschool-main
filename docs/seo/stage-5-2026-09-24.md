# Stage 5 speed and measurement — 24 September 2026

## Release status and measurement boundary

The Stage 2 and Stage 3 changes were present in the development code when this work started, but were not yet on the published site. The live production measurements below therefore describe the **older published build**, not a Stage 3 baseline. Do not claim a before/after Core Web Vitals or ranking gain from comparisons between the published site and local builds. Rebaseline the published site after the next release before attributing changes to Stage 5.

An earlier single run of the same routes measured `/` at score 69, LCP 1656 ms, TBT 2251 ms, CLS .001 and `/contact` at score 35, LCP 2982 ms, TBT 3192 ms, CLS .500. The contact page's instability makes a single-number improvement claim particularly unreliable.

Three direct mobile-user-agent GETs from this workspace to each published path measured HTML TTFB of 212–242 ms for `/`, 167–244 ms for `/contact`, and 174–198 ms for `/blog`. This is **one geographic vantage point**, not a geographic distribution.

Published campaign URLs with UTM fields redirected to URLs without those fields, including the legacy Google enquiry URL. Both browser and Googlebot HTML sampled on `/contact` returned `Cache-Control: no-store` and `CF-Cache-Status: DYNAMIC`; bot responses also included CDN `no-store` and `Vary: User-Agent, Accept-Encoding`. No HTML caching policy was changed.

The public PageSpeed field-data request returned a daily-quota error. No CrUX/INP field baseline was available, so no field trend is inferred. Third-party tag traffic appeared during lab runs; neither that traffic nor an audit status alone establishes failed or duplicate conversion delivery.

## Development candidate

- Campaign and supported click parameters now survive canonical and legacy redirects and are retained for up to 30 minutes within the browser tab. Forms include campaign context in first-party contact requests; analytics form events exclude parent/child identifiers and click IDs. Manual page views retain only approved campaign query keys so campaign acquisition is not lost and unrelated query values are not sent.
- The homepage hero preload and static image no longer load on non-home routes. The contact map module and Three.js load when the map nears the viewport rather than at initial page load. No broad HTML caching or tag-container removal was made.
- Source and medium remain stored with the lead. The notification email includes the campaign, and the asynchronous CRM attempt receives it; the existing database and Sheets layout do **not** persist the campaign. The new server code does not depend on a new database field, so a delayed schema change cannot break ordinary enquiries. CRM failure remains independent of lead storage and mail/Sheet results. Click identifiers remain request-only and are not stored with the lead or sent in analytics conversion events. Campaign *keys and values* are screened before GA page views, form views and conversions: compact campaign slugs are accepted, while email-like strings, phone-like digit sequences and names containing spaces are excluded. Raw campaign values are retained for the first-party request.

## Functional checks and delivery limitations

Redirect checks against the running development app reached `/ad-google` with source, medium, campaign and a synthetic click identifier intact; the canonical destination did not redirect again. Focused automated tests cover redirect loops, bounded attribution across navigation, a single manual page view with only approved campaign query keys, and the absence of parent/child identifiers and click IDs from form-conversion events. The build and static-ad tracking checks passed.

A mobile browser pass at 390 × 844 showed the contact form, a home hero after navigating via the site, and attribution retained in session storage after returning to contact without query parameters. It also showed that the contact page did not initially fetch Three.js. **The browser pass submitted no lead:** the test plan had incorrectly requested “General Enquiry,” which is not a contact-form programme option. This was a test-plan error, not a verified form defect.

One clearly labelled synthetic lead was submitted to the **development** contact endpoint using the valid Nursery programme, a dummy phone number and synthetic campaign parameters. It returned HTTP 201 with `success`, `emailSent` and `sheetAppended` all true; server logs confirmed the email and Sheet operations. The development environment lacks CRM submission credentials, so its asynchronous CRM handoff reported failure. This does not establish CRM delivery or a live production conversion. A successful endpoint response and unit-checked analytics payload are not equivalent to an end-to-end observed browser conversion event.

A **second** labelled synthetic enquiry returned HTTP 201 with email and Sheet delivery both true. During verification, an optional campaign column was briefly added to the development database and the second test value was saved there. A release review found that depending on that new field could block *all* production enquiries if the code and schema were released out of order, so the field was removed from the application schema and storage code before delivery. The extra development-only column remains untouched to avoid deleting the test record; current code does not read or write it, and there is no production schema dependency. Campaign persistence in the database is **not** a delivered feature.

A **third** labelled synthetic enquiry, with no campaign parameters, was submitted after removal of that code dependency. It returned HTTP 201 with both email and Sheet delivery flags true. This checks the current no-campaign development path but cannot replicate the published database or prove production delivery before release.
