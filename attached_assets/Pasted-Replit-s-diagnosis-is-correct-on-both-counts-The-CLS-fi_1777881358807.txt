But before you go into the Cloudflare dashboard, there's one premise that should be tested, because if it's wrong it changes the fix.
Test the Zaraz hypothesis before acting on it
Replit said "the culprit is almost certainly Cloudflare Zaraz." That's plausible but not confirmed. There are at least three things that inject private and Set-Cookie at the Cloudflare layer:

Zaraz with server-side cookies enabled
Cloudflare Bot Management or Bot Fight Mode (sets __cf_bm typically, but other variants exist)
A Cloudflare Worker sitting in front of the origin
Cloudflare Apps (legacy product, but some sites still have them)

The cookie is named GAESA. That naming pattern — GA prefix — strongly suggests it's a Google Analytics-related cookie set via Zaraz's Google Analytics integration. So Zaraz is the most likely answer. But "most likely" is exactly the kind of reasoning that landed us with three regressions in a row.
Spend 60 seconds confirming before clicking around in dashboards:
bash# Look at all the headers coming back, not just the ones we've been grepping
curl -sI -A "Mozilla/5.0 (iPhone)" https://www.rainbowpreschools.com/ | sort

# In particular look for:
#   server: cloudflare
#   cf-ray: ... 
#   any header starting with "cf-" or "x-" you don't recognize
#   any "via:" header
#   any "report-to" header pointing at a Worker
bash# Check whether a Worker is in the path. Workers usually leave fingerprints
# in cf-ray timing or in a custom response header.
curl -sI https://www.rainbowpreschools.com/ | grep -iE 'cf-worker|x-worker|cf-cache-status|server'
In the Cloudflare dashboard, before touching Zaraz, check:

Workers Routes (Workers & Pages → your zone → Routes) — is there a Worker bound to www.rainbowpreschools.com/*?
Rules → Transform Rules → Modify Response Header — is anything rewriting Cache-Control or adding Set-Cookie?
Zaraz → Tools — list what's configured there. If Zaraz has zero tools, it's not the culprit.

If Zaraz has Google Analytics or Google Ads configured with server-side cookies, Replit's fix is right. If Zaraz is empty, you need to keep looking — Option B (the Cache Rule) would still work as a workaround, but you'd be papering over a different problem.
On Option A vs. Option B
Replit framed Option A (disable Zaraz server-side cookies) as "cleaner" and Option B (Cache Rule that ignores Set-Cookie) as "faster." I'd push the framing slightly:
Option A is correct if you want measurement to keep working. Disabling server-side cookies in Zaraz means GA goes back to client-side cookies (_ga, _ga_<id>), which is the standard mode anyway and works fine. Nothing breaks; you just stop double-instrumenting.
Option B is a workaround. It tells Cloudflare to ignore Set-Cookie on cacheable responses, which means:

The cache fix works ✓
But the GAESA cookie is still being set on every response — you're just hiding it from the cache decision
Every response still pays the cost of generating that cookie
Under DPDP, you have a server-set cookie of unknown function being sent to every visitor regardless of consent state. That's a privacy review item I'd want to clear, not paper over.

So: do Option A if you can identify the source. Use Option B only as a temporary unblock if Option A turns out to require deeper investigation.
What should happen post-fix
Once whichever fix is in place, the verification sequence:
bash# Step 1: confirm Cache-Control is now public (not private)
curl -sI -A "Mozilla/5.0 (iPhone)" https://www.rainbowpreschools.com/ | grep -i cache-control
# Expected: cache-control: public, max-age=0, s-maxage=300, stale-while-revalidate=86400

# Step 2: confirm Set-Cookie is gone (Option A) or still present but cache works (Option B)
curl -sI -A "Mozilla/5.0 (iPhone)" https://www.rainbowpreschools.com/ | grep -iE 'set-cookie|cf-cache-status'

# Step 3: edge cache hit on second request
sleep 30
curl -sI -A "Mozilla/5.0 (iPhone)" https://www.rainbowpreschools.com/ | grep -i cf-cache-status
# Expected: HIT

# Step 4: bot path still bypasses cache (we don't want bot HTML cached for humans)
curl -sI -A "Googlebot/2.1" https://www.rainbowpreschools.com/ | grep -iE 'cache-control|cf-cache-status'
# Expected: cache-control: private, no-cache  AND  cf-cache-status: DYNAMIC or BYPASS
# This was working before — confirm it still works after the change.

# Step 5: bot still gets the JSON-LD-laden SSR
curl -s -A "Googlebot/2.1" https://www.rainbowpreschools.com/ | grep -c 'application/ld+json'
# Expected: > 0
Step 4 is the easy-to-miss one. If you go with Option B (Cache Rule that ignores Set-Cookie), make sure the rule's hostname/path matchers don't sweep up bot SSR responses. Bot-rendered HTML at the edge cache served to a human visitor is a real failure mode — search snippets ranked from the bot variant, served to humans, getting indexed as your canonical experience. Pin the cache rule to "Cache-Control header contains 'public'" or to specific paths, so the bot-SSR private responses are excluded by the rule's own matcher.
On the field data, set expectations correctly
Replit said field CLS will drop "over the next 2-4 weeks." That's the right shape but here's the more precise version:

Field CWV is a 28-day p75 rolling window
It updates daily, not weekly — but each day shifts the window by one day
For a clean fix that takes effect on day 0, you'll see:

Day 1-7: barely visible movement (1 of 28 days is post-fix)
Day 7-14: clear downward trend
Day 21-28: number stabilizes at the new floor
Day 28+: full window is post-fix



So don't panic if it's still 0.40+ a week from now — that's expected. But if you don't see any downward trend in the daily CrUX history (use pagespeed.web.dev and check "history" link, or Search Console CWV report) within 5-7 days, that means real users are still seeing CLS, and you need to dig further.
Search Console CWV report is the right place to watch this — it shows the daily trend, not just the current 28-day p75.
