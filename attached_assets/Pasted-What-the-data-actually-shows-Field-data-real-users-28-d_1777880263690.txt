The CLS field number is the alarm
Field CLS is 0.46, lab CLS is 0.499. They're nearly identical. That means the cookie banner fix you deployed did not actually take effect in production, or there's a second CLS source the banner fix didn't address.
Replit's local test showed CLS dropping to 0.001. Production says 0.46. One of these is wrong, and field data is real users, so field data wins.
Three possible causes, in order of likelihood:
1. The deployed bundle doesn't contain the banner fix. Replit confirmed the file changed locally, but if the build cached an older version, or the deploy didn't actually pick up the new component, production is still running the mount-at-800ms version. Check first.

2. There's a second CLS source that isn't the banner. The PSI report shows a "Layout shift culprits" section (Image 3) — open it. That's the authoritative answer to what's shifting. Common second sources:

Web fonts swapping (FOUT) — text reflows when the custom font loads
The "Admissions Open" badge or the "Book Visit" / "Request Callback" buttons appearing late
Hero image dimensions not matching reserved space — the filmstrip in Image 3 shows blank frames before the hero appears, which is suspicious
JSON-LD or other late-injected DOM elements

3. Field data lag. Field CLS is a 28-day p75. If the deploy happened in the last day or two, the 28-day window still includes 26+ days of pre-fix data. This is real, but it's not enough to explain a near-zero shift. If the fix worked, you'd see some movement in the p75 already.
The LCP picture is more nuanced — and actually slightly encouraging
Field LCP 3.6s. Lab LCP 9.3s. Those numbers can legitimately diverge by that much, but the direction tells you something:

The lab number got worse (was 7.9s, now 9.3s) — but lab is one synthetic run with no warm cache, no edge cache, on a throttled simulation. Lab LCP of 9.3s on a fresh Lighthouse run with no Cloudflare cache hit is actually consistent with cache headers being set correctly but the response still going DYNAMIC because of the GAESA cookie. The first hit always misses the edge cache; that's the worst case.
The field number is 3.6s. That's bad (target is < 2.5s, "needs improvement" up to 4.0s) but it's the real-user p75. If pre-deploy field LCP was substantially worse, 3.6s might be an improvement that just hasn't fully propagated through the 28-day window yet.

If the culprit isn't the banner, the banner fix worked but there's a separate CLS source we didn't address. Common culprits to check:

Step 3 — Find the GAESA source (10 minutes, parallel)
Replit's grep on the codebase found nothing. That confirms it's external. Most likely sources:

Cloudflare Zaraz — go to Cloudflare dashboard → Zaraz → check if any tools are configured to set cookies on the origin response
Cloudflare Bot Management / Bot Fight Mode — these don't typically set named cookies on the origin response, more likely to set __cf_bm (different name)
A reverse proxy / WAF rule — check Cloudflare → Rules → Transform Rules → Modify Response Header

Once you find it, either remove it or add the Cloudflare Cache Rule to ignore Set-Cookie for HTML responses. This is now blocking the LCP fix — without it, s-maxage=300 is doing nothing.
Step 4 — Don't panic about the lab Performance score of 18
Lab Lighthouse on a SPA with cold edge cache, simulated slow 4G, and 4x CPU slowdown is the worst-case for any site. The metric that matters for your business priorities (local SEO ranking) is field CWV from CrUX, not lab Lighthouse. Google ranks on field data.
That said: field CLS 0.46 is a genuine problem for ranking, and field LCP 3.6s is borderline. So we do need to fix things — just don't let the lab "18" send you into an emergency response that overshoots.
Why this happened
Looking back at the deploy sequence: we pushed five changes simultaneously, and verification was structured around lab Lighthouse against a local preview. Local preview can't measure Cloudflare cache effects (no CF), and lab CLS on a single run can miss issues that show up in field data because real users see different timings.
Two process changes worth making after this is stable:

Always check the deployed bundle contains the change, not just the local file. A curl | grep on a string unique to the new code, run after deploy, would have caught case (1) above in 30 seconds.
Field CWV beats lab CWV for go/no-go decisions. The PSI "field data" panel is the truth. Lab is for diagnosing why something is slow, not whether it's slow. The pre/post-deploy comparison should be field-vs-field (Search Console CWV report has the trend graph) — even if you have to wait a few days for the field window to update.
